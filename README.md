# xyno-sandbox.nvim

A Neovim plugin that runs a command-line coding agent inside a bubblewrap sandbox and refuses to start it without one. Linux only.

## Why

Command-line coding agents that run without permission prompts have all of your privileges. I did not want that from inside my editor, so I wrap them: the filesystem is read-only except the project and a scratch directory, `$HOME` shows only an allowlist of toolchain paths, credentials and project secrets (`.env`, keys) are hidden, host sockets are masked, secret environment variables never exist inside,  network egress is default-deny with a short hostname allowlist, and anything that would later run outside the sandbox (git hooks, editor task files, direnv, cargo config, the agent's own settings) is locked read-only in the project root and in the subdirectories that exist (a file the agent newly creates in a subdirectory is reported when the run ends, not prevented: see Residual risks). Where no sandbox can be created, the agent does not start. That fail-closed default is the point of the plugin.

The policy knows the config, cache and state directories of one agent CLI, but `wrap()` takes any command; for other agents those paths are simply absent.

## Requirements

- Neovim 0.12+
- Linux with [bubblewrap](https://github.com/containers/bubblewrap) (`bwrap`) on `PATH` and unprivileged user namespaces enabled
- no other plugin

## Install (lazy.nvim)

```lua
{
  "xynorash/xyno-sandbox.nvim",
  cmd = { "XynoSandboxStatus", "XynoSandboxPolicy", "XynoSandboxApprovals", "XynoSandboxReview", "XynoSandboxRun" },
  opts = {},
  -- no dependencies on other plugins
  keys = {
    { "<leader>as", "<Cmd>XynoSandboxStatus<CR>", desc = "Sandbox status" },
    { "<leader>ap", "<Cmd>XynoSandboxPolicy<CR>", desc = "Sandbox policy" },
  },
}
```

A lualine component that shows the state (`sandbox: on`, `sandbox: checking`, `sandbox: OFF`, `sandbox: refused`, plus `x2` for two running sandboxes):

```lua
lualine_x = {
  { require("xyno_sandbox").statusline, color = function() return require("xyno_sandbox").statusline_hl() end },
}
```
`statusline()` never blocks and never errors, so it also works in a plain `statusline` option.

## Options

`setup(opts)` with the defaults:

```lua
require("xyno_sandbox").setup({
  sandbox = true,            -- false: deliberate opt-out, run unsandboxed even where bwrap works
  allow_unsandboxed = false, -- true: run unsandboxed when NO working backend exists (never disables a working sandbox)
  keymaps = false,           -- false, or { status = "<lhs>", policy = "<lhs>" }; no global keymap is set by default
  commands = true,           -- register the :XynoSandbox* commands
  preview = "once",          -- policy preview before a launch: "always" | "once" (per project) | "never"
  strip_skip_permissions = false, -- true: remove --dangerously-skip-permissions from the command
  agent_cmd = nil,           -- command shown by :XynoSandboxPolicy before anything was launched
  home = "allowlist",        -- "allowlist": $HOME is empty except explicitly allowed paths | "denylist": all of $HOME readable except the hidden credentials
  expert_exceptions = false, -- true: "env" exceptions for LD_PRELOAD, PATH, ... may be approved
  network = "filtered",      -- "filtered": no direct network, HTTPS only through the allowlist proxy | "open": unrestricted (shown as OPEN)
  allow_hosts = nil,         -- nil: require("xyno_sandbox").default_hosts; a list REPLACES the defaults
  policy = {                 -- ADDITIVE policy lists (nothing can be removed from the built-in policy)
    readonly = {},           -- more read-only locks: project-relative, absolute or ~/ (locked when present)
    writable = {},           -- more writable paths: absolute or ~/ (never "/" or $HOME)
    hidden = {},             -- more hidden paths: absolute or ~/ (dir: empty tmpfs, file: empty file)
    guard_dirs = {},         -- project-relative dirs masked read-only when absent
    guard_files = {},        -- project-relative files bound to an empty read-only file when absent
    scrub = { contains = {}, prefix = {}, exact = {} }, -- more environment variable names to strip
    scan_depth = 8,          -- how deep nested .git and workspace members are looked for (1 to 32)
    home_allow = {},         -- more $HOME paths shown read-only in home = "allowlist" mode
    keep_run = {},           -- paths below /run or /var/tmp bound back read-only (they must hold no sockets)
    git_write = false,       -- true: the agent can git add / git commit (see "Git is read-only" below)
    project_secrets = true,  -- hide .env, *.pem, ... in the project (false: do not)
    secret_files = {},       -- more project file name globs to hide, e.g. "*.token"
    secret_allow = {},       -- project file names or project-relative paths that are never hidden
    content_scan = true,     -- look inside project files for known token formats and hide the ones that have one (false: do not)
    tree_secrets = true,     -- hide secret NAMES inside the trees shown whole from $HOME (a $PATH entry's parent, toolchains); false: do not
    claude_share = {},       -- names below ~/.claude shown read-only (e.g. "settings.json", "CLAUDE.md"); allowlist view only
    symlinks = "warn",       -- "warn": list links that leave the project | "refuse": do not start while one has a readable target
  },
})
```

`setup()` validates its options: an unknown key, a wrong type, a relative `writable`/`hidden` path, a `..`, a path that would expose `/` or `$HOME`, or a bad variable name raises an error and changes nothing.

Only the booleans `false` and `true` count for `sandbox` and `allow_unsandboxed`. `0`, `1`, `"false"` and `"true"` do not. Either may also be a function returning the boolean, evaluated at every call.

| Situation | Result |
| --- | --- |
| Linux, `bwrap` present and user namespaces work (checked by a real probe) | sandboxed (only `sandbox = false` turns it off) |
| No backend (Windows, macOS, Linux without `bwrap`) | refused: `wrap()` returns `nil, reason` |
| `bwrap` present but it cannot create a namespace (kernel setting, AppArmor, container) | refused, with the reason and a fix hint |
| No working backend and `allow_unsandboxed = true` | runs unsandboxed |
| `sandbox = false` anywhere | runs unsandboxed |

Every explicitly unsandboxed run through `:XynoSandboxRun` or `run()` warns.

### The permission-bypass flag

Agents that run without permission prompts (`--dangerously-skip-permissions`) rely on the sandbox as the only barrier. The preview says so on its own line: `Agent permission prompts: OFF (--dangerously-skip-permissions)`. With `strip_skip_permissions = true` the flag is removed from the command before it runs and the line reads `ON`. The agent then has to ask before acting, which a non-interactive `--print` run cannot do; what a given agent does then is not something this plugin checks. Without that setting the command is run as given.

## What the sandbox hides

Findings of an independent red team, each reproduced by running it, drove these. Every one has a spec in `tests/` that fails when the fix is removed (see the [CHANGELOG](CHANGELOG.md) for the mutation checks).

**The environment never reaches the sandbox.** bwrap itself is started as `env -i NAME=value ... /path/to/bwrap ...` with only the allowed variables. `env -i` has no `$PATH`, so env would find a bwrap only in libc's default path: the launcher names the ABSOLUTE path of the binary the readiness check found (`exepath`, also for NixOS, Guix, `~/.local/bin`, Homebrew on Linux) and the probe runs that same binary (round 6). Stripped values (`GITHUB_TOKEN`, `AWS_SECRET_ACCESS_KEY`, `ANTHROPIC_API_KEY` with a file based login, `$NVIM`, ...) are not in bwrap's environment either, so `/proc/1/environ` (bwrap is pid 1 of the sandbox) and every other `/proc/*/environ` hold none of them. Before, `--unsetenv` removed them from the agent's environment only and `/proc/1/environ` still had the original one. Values never appear in the command line, the preview or the log. The scrub looks at the name (`TOKEN`, `SECRET`, `PASSWORD`, `JWT`, `COOKIE`, `BEARER`, `*_KEY`, `*_DSN`, `*_SESSION`, `*_AUTH`, `AWS_*`, `GITHUB_*` ...) **and at the value**: a variable whose value is a known token format (`ghp_...`, `AKIA...`, `sk-ant-...`, a private key header) or has credentials in a URL (`redis://:password@host`) is stripped whatever it is called. A secret in an unknown format under an unlisted name (`MYAPP_X=hunter2`) is not found; list it in `policy.scrub`.

**Git is read-only by default, so the agent cannot commit.** Every `.git` in the project is mounted read-only: `git log`, `git status`, `git diff` work (with your `~/.gitconfig` minus credentials), `git add` and `git commit` fail ("Read-only file system"). That is deliberate: a writable `.git` lets an agent plant a hook, `core.fsmonitor` or an alias that your next unsandboxed `git status` runs. **Git write mode** (`policy = { git_write = true }`) is the opt-in middle way: a `.git` directory of the project stays writable (index, objects, refs, HEAD, logs: `git add` and `git commit` work) while `hooks/`, `config`, `info/` and `config.worktree` (and the same four in every submodule git directory below `modules/`, down to 4 levels) stay read-only, so nothing that makes git run code or change its behaviour can be planted. Locking those four is not enough on its own, which an independent run showed (round 9): `.git` itself was not a mount point, so `mv .git .git.old && mkdir .git && cp -a .git.old/. .git/` rebuilt it with a hook and `core.fsmonitor`; and a writable `.git/commondir` pointed git at another common directory whose config ran a command on your next unsandboxed `git status`. Both are closed: every writable git directory (and `modules/`) is a mount point of its own (`--bind d d`, which cannot be renamed), `commondir` is pinned to a file holding `.` (the directory itself) or locked when it exists, and `rebase-merge/`, `rebase-apply/`, `sequencer/` (an `exec` line that a later `git rebase --continue` runs), `remotes/`, `branches/` and `worktrees/` are read-only when present and an empty read-only directory when absent. The price: `git rebase`, `git cherry-pick` of several commits, `git am`, `git worktree add` and `git submodule add` do not work inside the sandbox in this mode (run them outside). **Allowlist (round 9, second pass).** An ABSENT `config.worktree` was not covered (git reads it as a config file when `extensions.worktreeConfig` is set, so `core.fsmonitor` or `core.sshCommand` there would run on your machine): it is now an empty read-only file when absent. The writable top-level names of a git directory are an allowlist (`plan.GIT_WRITE_ALLOWED`: `HEAD`, `ORIG_HEAD`, `FETCH_HEAD`, `COMMIT_EDITMSG`, `TAG_EDITMSG`, `SQUASH_MSG`, `AUTO_MERGE`, `CHERRY_PICK_HEAD`, `REVERT_HEAD`, `packed-refs`, `shallow`, `index`, `objects`, `refs`, `logs`, `description`, `lfs`, `rr-cache`, `gc.log`, `gc.pid`, `lost-found`, and `MERGE_*`, `BISECT_*`, `NOTES_MERGE_*`, `sharedindex.*`, `*.lock`). Every other name that EXISTS at launch is read-only (an unknown `svn/`, a daemon socket). A NEW name outside it cannot be stopped by a mount, because the directory has to stay writable for `index.lock`; it is checked when the run ends: the new top-level names of every git directory (and any new directory below `modules/`) outside the allowlist are copied to the quarantine, removed and the project is marked, like a planted `.envrc`. So the guarantee is: for names git consults that can run a command (`config`, `config.worktree`, `hooks/`, `info/`, `commondir`, `modules/`, rebase / sequencer state, `worktrees/`, `remotes/`, `branches/`) the mounts hold WHILE the run is on; for any other new name the guarantee starts when the run ends, so an unsandboxed git run in this project WHILE the agent still works could read a name the audit has not removed yet. What is not audited: the content of the allowed names (a ref, an object, `index`, `logs/`, `objects/info/alternates`, `refs/replace`), because they are data to git, not commands; that is a judgement from reading git's documentation of config files, hooks, attributes, filters, fsmonitor, credential helpers, editors and `gpg.program` (all of which are configured in `config`, `config.worktree`, `hooks/` or `info/attributes`), not something I proved for every git version. It is not free: the agent can still rewrite history and move refs of that repository (`git reflog` recovers them), and a `.git` file or a gitdir outside the project (worktrees) stays fully locked. Other writable files inside `.git` (`objects/info/alternates`, `refs/replace`, `shallow`) can change what git SHOWS but do not make it run a command; that is a judgement from reading git's documentation, not a spec. The preview (`:XynoSandboxPolicy`) shows a "Git write mode" section when it is on. Checked by `tests/git_write_spec.lua` with a real bubblewrap run (hook, config, info writes and `git config` refused; commit works; `.git` and `modules/` cannot be renamed, `commondir` and the rebase / sequencer / worktrees state cannot be created, and an unsandboxed `git status` on the result runs nothing). `tests/round10_spec.lua` pins every allowlist entry and runs checkout -b, reset --hard, pack-refs, tag, merge, fetch and gc, and a host-side battery (status, log, fsck, gc, commit, fetch, checkout, submodule status, maintenance) after planting attempts. A run ended by kill -9 has no end-of-run sweep, so a name planted during it stays until you look; LFS, `gpg.program` and `sshCommand` are not exercised by a spec.

**Host unix sockets are not connectable.** `/run`, `/var/tmp` (and `/var/run` when it is a real directory) are replaced by an empty tmpfs, like `/tmp`. That removes the ssh-agent, systemd varlink and journal sockets, polkit, dbus, docker, tmux, `/run/user/<uid>` (wayland, pipewire, the session bus, gpg-agent) in one rule instead of a list. A socket named by `$SSH_AUTH_SOCK`, `$GPG_AGENT_INFO`, `$XDG_RUNTIME_DIR`, `$DBUS_SESSION_BUS_ADDRESS`, `$WAYLAND_DISPLAY` or `$NVIM` that lives elsewhere is hidden too, and sockets inside the project are hidden, **also inside `target/`, `node_modules/`, `.cache/` and `.git/` and down to 24 levels** (a separate search with its own budget of 30000 directories; when that runs out the plan says so and a socket further down stays connectable). Only the proxy's socket (filtered mode) can be connected to; a spec runs a Python `connect()` sweep over the sandbox and fails on any other. `/run/current-system` and `/run/opengl-driver` (NixOS) are bound back read-only; add more with `policy.keep_run`, knowing that a socket there bypasses the network filter. To allow one socket use `keep_run`, not an exception.

**`$HOME` is an allowlist by default.** `home = "allowlist"` puts an empty tmpfs over `$HOME` and binds back, read-only, only: `~/.cargo`, `~/.rustup`, `~/.local/share/claude`, `~/.gitconfig`, `~/.config/git`; directories named by `CARGO_HOME`, `RUSTUP_HOME`, `GOROOT`, `GOPATH`, `NVM_DIR`, `PYENV_ROOT`, `BUN_INSTALL`, `JAVA_HOME`, `ANDROID_HOME` and similar when they are under `$HOME`; `$PATH` entries under `$HOME` (and the toolchain root above a `.../bin` entry, so `npm` next to `node` works); the agent binary (resolved through `$PATH` and its symlinks); and whatever you add with `policy.home_allow`. The project, the scratch directory and the agent's own writable paths come on top. Everything else in `$HOME` (documents, other projects, `~/.ssh`, browser profiles, shell dotfiles) does not exist inside. Writes to `$HOME` land on the throw-away tmpfs. The preview lists every allowed path under "Home view". A spec runs a fake agent that needs `cargo` and `rustc` (builds and runs a crate), a `git log`, and the installed agent CLI's `--version` inside this view. Because that works, it is the default; `home = "denylist"` restores the old view (all of `$HOME` readable except the hidden credential list). Credentials inside an allowed tree (`~/.cargo/credentials.toml`, `~/.config/git/credentials`) stay hidden. **A directory that is shown whole is searched for secret names**: `$PATH` entries such as `~/dotfiles/bin` or `~/.npm-global/bin` show their parent, and inside every shown tree (four levels, package caches such as `registry`, `node_modules` and `target` skipped, at most 600 directories per tree and 2400 in all, breadth first) the project's name list applies (`.ssh/`, `.npmrc`, `credentials`, `id_rsa*`, ...) plus directories called `secrets`, `.secrets` or `private-keys`; they are hidden and listed in the preview (`secret in the shown tree ...`). That is by name only, never by content, and a tree beyond the budget gets a note in the plan. `policy.tree_secrets = false` turns it off. If a tool you need is missing inside, add its directory to `policy.home_allow`; the failure is "not found", not a leak.

**Project secrets are hidden.** In the project (down to `policy.scan_depth`, skipping `target`, `node_modules`, `.git`, `.venv`): `.env`, `.env.*`, `*.env`, `*.pem`, `*.key`, `*.p12`, `*.pfx`, `*.jks`, `*.kdbx`, `.npmrc`, `.yarnrc.yml`, `.pypirc`, `.netrc`, `.git-credentials`, `.htpasswd`, `credentials`, `credentials.*`, `secrets`, `secrets.*`, `id_rsa`/`id_ed25519`/..., service-account and client-secret JSON, `*.tfvars`, `*.tfstate`, `kubeconfig`, and the directories `.aws`, `.ssh`, `.gnupg`, `.kube`, `.azure`, are replaced with an empty read-only file or directory, so the agent reads nothing, cannot write, move or delete them. Templates (`.env.example`, `.env.sample`, `.env.template`, `.env.dist`) stay readable. This is a name list: a secret in a file called `config.yml` is not found. Add globs with `policy.secret_files`, let names through with `policy.secret_allow`, turn it off with `project_secrets = false`. In the preview (`e`) each hidden secret can be shown for one launch or for the project like any hidden path, logged like every exception.

Also by name: `.vault-token`, `.env~` (editor backups), `.envs/`, `auth.json`, `rclone.conf`, `.terraformrc`, `.secret`, `.npmrc.*`, `id_rsa*`/`id_ed25519*` variants (`.bak`, `_sk`; public `*.pub` keys stay readable), `wallet.dat`, `creds.json`, `oauth_token`, `sa.json`, `serviceaccount*.json`, and by path where the base name says nothing: `.docker/config.json`, `.config/gh/hosts.yml`, `.composer/auth.json`, `.m2/settings.xml`, `.gradle/gradle.properties`, `.kube/config`.

The default name list also covers what frameworks and clouds call their secrets: `.dev.vars`, `serviceAccountKey.json`, `firebase-adminsdk*.json`, `google-services.json`, `GoogleService-Info.plist`, `wp-config.php`, `local.settings.json`, `application-prod.*`, `appsettings.Production.json`, `master.key`, `.pgpass`, `.my.cnf`, `.s3cfg`, `.yarnrc`, `*.ppk`, `*.p8`, and data files named `token`, `api_key(s)`, `apikey`, `password(s)`, `secret`, `private_key` ... with a data extension (`token.txt`, `api_keys.json`; not `tokenizer.rs` or `api_key.rs`).

**Secrets that no name gives away.**
- *Git remotes.* A token in a remote URL (`https://user:TOKEN@github.com/x/y.git`, also in `[url "..."]` headers and submodule configs) is not shown: the sandbox mounts a generated, read-only, 0600 copy of every `.git/config` it locks (also `~/.gitconfig` and `~/.config/git/config` in the allowlist view) over the real one. The copy has URL credentials removed (for http(s), the whole user info; for other schemes the password), every `credential.helper` (a `store --file=` path, a shell helper) and `http.extraHeader`/`password`/`token`/`askpass` line dropped. `git log`, `git status` and `git remote -v` work; `git push` inside the sandbox has no credentials, by design. The copy is deleted on release; the real file is never touched. An unreadable config becomes an empty copy, not the original.
- *Content scan.* When the preview (or a launch) is built, the project is scanned for known token formats: AWS access key ids and secret keys, GitHub (`ghp_`, `github_pat_`), GitLab (`glpat-`), Slack tokens and webhooks, Stripe live keys, OpenAI and Anthropic keys, Google API keys, npm tokens, SendGrid keys, PEM/OpenSSH/PGP private key headers, and `https://user:password@host` URLs. A file with a hit is hidden like a secret by name (empty read-only file), listed in the preview with the *kind* (`looks like a GitHub token`, never the value), and can be shown again with `e` (approve-to-unhide) or `policy.secret_allow`. A token is found after `=`, `:`, quotes, brackets, commas, a JSON escape (`\n`), CRLF line ends, and glued to the end of a word (`tokenghp_...`, `idAKIA...`: a token with a distinctive prefix is one wherever it starts; an AWS key id is not looked for inside an upper-case word); private key headers are found in any case, with tabs or several spaces and glued to their neighbours (`key=-----BEGIN RSA PRIVATE KEY-----MIIE...`). GitHub, GitLab, npm and Hugging Face tokens count with a minimum length (longer ones exist). Also known since round 5: Hugging Face (`hf_`), DigitalOcean (`dop_v1_`), Shopify (`shpat_`), Slack app tokens (`xapp-`), Stripe test keys (`sk_test_`) and the legacy `sk-` + 48 characters OpenAI keys. The scan is bounded: at most 4000 files, 6000 directories, 256 KB per file, 24 MB read, 8 levels deep and 400 ms; `target`, `node_modules`, `.git`, `dist`, `build`, `vendor`, virtualenvs and files with a NUL byte or over 256 KB are skipped, symlinks are not followed, `$HOME` and shared directories are never scanned. When a limit stops it, the preview says `STOPPED` and the plan carries a note. Unchanged files are not read again on the next plan. `policy.content_scan = false` turns it off.
- *What it cannot catch.* A plain password, a generic API key or JWT, a database URL, anything in a format it does not know, a secret in a file over the size limit or in a binary, in a skipped directory, past a budget, encoded or split over lines (one exception: a private key header inside base64, as in a Kubernetes secret or a CI variable, is found at all three alignments; not found: a header that is URL-encoded (`%2D%2D...`), an HTML entity, hex, base64 that is itself line-wrapped inside the header or encoded twice, UTF-16 text), and a secret that appears after the sandbox started. Known token formats only, on purpose: no entropy guessing, so the preview does not fill with hashes and ids. Documentation examples are ignored only when the matched token itself says so (`AKIAIOSFODNN7EXAMPLE`, `ghp_xxxxxxxx...`, a token containing `example`, `dummy`, `fake`, `your_`): a real token on a line that says `# example` or names `example.com` is still a hit. Lines of any length are read, in linear time (a 256 KB line of letters, hex or minified code takes about 30 ms; the URL pattern used to be retried from every letter, 64 KB took 16 s) and the 400 ms budget is checked inside a file too. Timings measured on the development machine (not a guarantee): a plan for a project with 100000 files in `target/` builds in about 0.07 s once the scan is cached (0.3 s the first time; `target/` is not listed), and with 100000 more files in a directory that is not skipped in about 0.25 s (the scan stops at its budget of 4000 files / 400 ms; the walk lists the directory once; matching every file name against the secret-name list used to take 18 s, and building a full path for every file to test the path-only secrets another 0.5 s). The preview says how many files it did not read at all (over 256 KB, a NUL byte in the first 1 KB: no file is skipped for its name or extension, so a private key in `key.lock`, `a.map` or `x.db` is found while the file is small). Not scanned, so a token there stays readable: those files, `node_modules`, `target`, `dist`, `build`, `vendor`, virtualenvs, `.git`, anything deeper than 8 levels.
- *Hard links.* Hiding a file hides one name. A hidden file with a link count above 1 is looked up in the scan: other names inside the project are hidden too, and the preview lists the file (`Hidden files that have other hard links`). Names outside the project (or beyond the scan) cannot be found: the plan says how many are unaccounted for, in the preview and as a note. A project file that is a hard link of a credential in `$HOME` (`ln ~/.ssh/id_rsa proj/innocent.txt`) is found too: the files of the hidden credential list (`.ssh`, `.aws`, shell histories, ... up to four levels, also of other owners' homes) are compared by inode with the project's multi-link files and the other name is hidden (`hard link of the credential ...`). The same comparison is made for the files that RUN outside the sandbox (the `plan.CODE_RUNS_OUTSIDE` list: `~/.bashrc`, `~/.gitconfig`, `~/.config/direnv`, `~/.claude/settings.json`, ... and the project's own locked `.git/config`, `.git/hooks`, `.envrc`, `.vscode`, `.cargo`): `ln ~/.bashrc proj/dot_bashrc` made the project name writable and every write went through to the real file; such a name is now hidden (an empty read-only file), with the reason `hard link of ..., which runs outside the sandbox`. The login file `~/.claude/.credentials.json` is part of that list: it is bound read-only (allowlist view) or locked read-only (denylist view), and a project hard link of it is hidden, because a hard link is a second, writable name for the same inode (the host file changed through `ln ~/.claude/.credentials.json proj/x` before round 5). The comparison looks at up to 1500 files (files before directories, so a big `~/.local/share/nvim` cannot crowd out `~/.bashrc`; the plan says when it stopped). Any other project file with a link count above 1 is reported in the plan (`plan.multilinks`) and as a note: its other names cannot be seen from here, so a write through it changes them. A link to a secret that is not on the credential list, or one in a directory the scan skips (`target`, `node_modules`), stays readable.
- *Symlinks named like secrets.* bwrap cannot mount on a symlink. A project `.env -> config/real.env` (or a dotfile manager's `~/.npmrc -> dotfiles/npmrc`) now hides the link's *target* by path (the link keeps working and reads the hidden target); a dangling link is skipped.

**`~/.claude` is a throw-away directory.** With the allowlist view the agent's state directory is an empty tmpfs inside the sandbox that holds only: its login file `~/.claude/.credentials.json`, bound read-only; this project's transcript directory (`~/.claude/projects/<project>`, writable, with its `memory` locked read-only); and whatever names you list in `policy.claude_share`, read-only. The transcripts of every other project, `history.jsonl`, `sessions`, the daemon keys, your `settings.json`, `CLAUDE.md`, hooks, plugins and skills are not there; what the agent writes elsewhere in `~/.claude` (todos, shell snapshots, caches) is gone when the run ends. Because the login is read-only, a token refresh inside the sandbox is not saved (a refreshed token that is not saved can invalidate the old one on the host; if the agent reports an expired login, start it once outside the sandbox). `~/.claude.json` is a private 0600 copy reduced to the current project's record (other projects' entries, their prompts and checkout paths are dropped), without `primaryApiKey`, `customApiKeyResponses`, the anonymous `userID`, the old global `history`, the account's e-mail address and name, the `env` and `headers` of every MCP server (user and project scope: a server that needs a token from its config does not work inside the sandbox; pass it through an approved `env` exception), and any string that is a known token format or has credentials in a URL, and any value whose key name says token, secret, password, api key, authorization, credential, bearer or cookie. The denylist view keeps the old behaviour (the whole directory writable, executable parts read-only; since round 5 the login file is read-only there too, so a token refresh is not saved in either view). The preview has a section `Agent state (~/.claude)` and one for `Agent transcripts`.

**Credential locations hidden in `$HOME` (denylist view; in the allowlist view `$HOME` is empty anyway).** `~/.ssh`, `~/.gnupg`, `~/.aws`, `~/.azure`, `~/.docker`, `~/.kube`, `~/.netrc`, `~/.npmrc`, `~/.pypirc`, `~/.git-credentials`, `~/.cargo/credentials*`, `~/.config/gh`, `~/.config/gcloud`, browser profiles, keyrings, shell histories and, since round 5, `~/.config/sops` (age keys), `~/.gem/credentials`, `~/.config/pypoetry/auth.toml`, `~/.pip/pip.conf`, `~/.config/pip/pip.conf` (index credentials) and `~/.npm/_logs`. The list is `plan.HIDDEN`; a credential file in a place nobody listed is readable in the denylist view.

**Other users' homes are hidden.** `/home` is an empty tmpfs (and the account's real home when it differs from `$HOME` and is outside `/home`), then `$HOME` is rebuilt on top of it (allowlist: tmpfs plus the allowed paths; denylist: bound back read-only). Toolchains, `$PATH` entries, the agent binary (and the targets of symlinks in a `$PATH` directory) and the nvim of the relay that live in a hidden home are bound back read-only, narrowly (never an owner's whole home, `~/.local` or `~/.config`), with that owner's credential list hidden inside them. A project inside another home stays writable. A project symlink that points into a hidden home reads nothing. The preview section is `Other users' homes hidden`.

**Symlinks out of the project are listed.** The walk finds links whose target is outside the project and the scratch directory and the preview lists them with whether the target is readable inside (`Project symlinks that leave the project`). In the allowlist view a link into `$HOME` points at nothing; a link to `/etc` or `/usr` is readable, as that is anyway. `policy.symlinks = "refuse"` makes the launch refuse while any such link has a readable target. Masking a link that is not secret-named is not offered: bwrap binds follow symlinks, so an overlay would hide the target for the whole sandbox, not only for the link. (A link that is *named* like a secret is handled: its target is hidden, see above.)

**The preview is the command line.** The preview is rendered from the same list of options (`plan.ops`) that becomes the command line. The base view (`--ro-bind / /`, `--dev`, `--proc`, `--tmpfs /tmp`), the masked sockets, the home view, the proxy directory and the `--setenv` names (values are not shown) have their own sections; `:XynoSandboxPolicy!` ends with the exact mount order, one bwrap option per line. `tests/preview_spec.lua` parses the real command line on its own and diffs it against the preview, and fails when any bind, tmpfs, setenv or flag is missing.

**Exceptions that would not work are refused.** A writable `<project>/.git` is mounted read-only again afterwards, so approving it did nothing while the log said approved; now it is refused ("no effect: ... is mounted read-only afterwards"), at approval time and in the plan. `unhide` needs a path the policy really hides; `env` needs a variable the policy strips. Also refused, whatever the scope: writable `/etc`, `/usr`, `/proc`, `/sys`, `/dev`, `/run`, `/run/user/<uid>`, every path of the *code runs outside the sandbox* categories below, a path below one and a parent that contains one (a writable `~/.config` would contain `~/.config/nvim`), also through a symlink that resolves there; there is no override for these (`expert_exceptions` only concerns environment variables); `unhide` of `/etc/shadow`, `/etc/sudoers`, `/etc/ssh/*`; shared system directories as a whole (`/tmp`, `/var`, `/var/tmp`, `/var/lib`, `/mnt`, `/media`, `/srv`, `/opt`, `/home`, `/dev/shm`; a project directory below them is fine) and any parent of a directory the sandbox replaces with an empty tmpfs (a writable bind comes after the masks and would bring the host's content back; `policy.writable` is checked the same way and ignored with a note); `env` exceptions for `LD_PRELOAD`, `PATH`, `LD_LIBRARY_PATH`, `BASH_ENV`, `NODE_OPTIONS`, `PYTHONPATH`, `RUSTC_WRAPPER` and similar unless `expert_exceptions = true`. Every refusal is logged with its reason.

**Where code runs outside the sandbox (refused as writable approvals, `policy.writable` entries and for hard links).** The list is generated from `plan.CODE_RUNS_OUTSIDE`: a path is a member when a program of yours, started later and outside the sandbox, reads it and *acts* on it. Categories: shell startup files (`.bashrc`, `.zshenv`, `.profile`, `.inputrc`, `~/.config/fish`, `~/.zsh`, ...); login session and desktop (`~/.config/autostart`, `~/.config/systemd`, `.xinitrc`, window manager configs, `~/.local/share/applications`); git (`.gitconfig`, `~/.config/git`); remote access (`~/.ssh`, `~/.gnupg`); editors and their plugins (`~/.config/nvim`, `~/.local/share/nvim`, `.vimrc`, Emacs, Helix, Zed, VS Code, JetBrains); terminals and multiplexers (`.tmux.conf`, kitty, alacritty, wezterm); environment and version managers (`~/.config/direnv`, `~/.config/mise`, `.tool-versions`, asdf, pyenv, nvm, nix); toolchains and package manager configuration (`~/.local/bin`, `~/.cargo/bin`, `~/.cargo/config.toml`, `~/.rustup`, `.npmrc`, pip, docker config); agents (`~/.claude/settings.json`, `hooks`, `commands`, `agents`, `skills`, `plugins`, `CLAUDE.md`, `~/.claude.json`, `.mcp.json`, other agents' config directories). Anything an unlisted program reads and runs is not covered: the list is a list of known places, not a proof.

**No placeholders in shared directories.** A project that is `/tmp`, `/var/tmp`, `/run`, `/` or a parent of `$HOME` is not mounted writable and gets no guard placeholders (the sandbox created an empty `.git`, `.envrc`, `.exrc`, `.mcp.json`, `.mise.toml` directly in `/tmp` for such a run, which then broke unrelated tools). The placeholders a launch may leave in a project are recorded in the live registry; the next launch removes those of a Neovim that died, if they are still empty.

## Network

Without a restriction, a prompt-injected agent can send out everything it can read (a read-only filesystem does not stop that). So the default is **default-deny egress, failing closed**.

How it works:

1. The sandbox runs with `bwrap --unshare-net`: its own network namespace with only a private loopback. No interface, no route, no resolver. Raw sockets, UDP, DNS, `ssh`, the host's `127.0.0.1` services and local database ports are all unreachable.
2. The only way out is a unix socket, bind-mounted read-only into the sandbox. Behind it runs a filtering forward proxy **inside Neovim** (pure Lua on `vim.uv`, `lua/xyno_sandbox/net.lua`). A launcher inside the sandbox first starts a ~80 line relay (`nvim -l relay.lua`) that listens on the sandbox's `127.0.0.1:3128` and pipes into that socket, waits until it listens, and only then `exec`s the agent. `HTTPS_PROXY`, `HTTP_PROXY`, `ALL_PROXY` (and lowercase) point at the relay; `NO_PROXY` is empty.
3. The proxy speaks only HTTP `CONNECT`. It decides by the **host name in the CONNECT line** and the port (default 443). It refuses raw IPs and anything that is not a DNS name (`1.2.3.4`, `0x7f.1`, `2130706433`, `[::1]`, `localhost`), names or ports that are not on the list, and plain HTTP. It resolves the name itself and refuses names that resolve to loopback, private, link-local (cloud metadata), CGNAT, multicast or documentation addresses, then connects to the address it checked (no second lookup). No TLS interception: it never sees the content and needs no CA.

Why a pure Lua proxy: no dependency (no `socat`, Python or Go binary to install and trust), it lives and dies with the editor that owns the agent, and a few hundred lines of CONNECT handling are short enough to audit. The price is that it shares Neovim's event loop. The same architecture is used by Anthropic's sandbox-runtime (bubblewrap with the network namespace removed, proxies reached over unix sockets).

**DNS.** The sandbox does no DNS. Clients that honour `HTTPS_PROXY` send the host name in `CONNECT` and the proxy resolves it, only for allowed names. Resolver sockets on the host (`systemd-resolved`'s varlink socket under `/run/systemd/resolve`, `nscd`, `avahi`, `dnsmasq`, `NetworkManager`, `unbound` under `/run`) are hidden, because `getent`/glibc would otherwise resolve through them from inside the sandbox: a spec runs `getent hosts` for a real name inside and it fails. A program that ignores the proxy variables simply has no network (it fails closed, it does not bypass).

**The allowlist.** Default (`require("xyno_sandbox").default_hosts`): `api.anthropic.com`, `platform.claude.com` (token refresh), `crates.io`, `static.crates.io`, `index.crates.io`. `github.com` is not on it. Replace or extend it:

```lua
local sb = require("xyno_sandbox")
sb.setup({ allow_hosts = vim.list_extend(vim.deepcopy(sb.default_hosts), { "github.com", "*.githubusercontent.com" }) })
```

Entries are `host`, `host:port` or `*.suffix` (a wildcard matches names below the suffix, not the suffix itself, and needs at least two labels). IP literals and `*.com` are refused by `setup()`. Prefer exact names: a wildcard under a domain others can register names in (`*.github.io`) lets the agent use those names as an exfiltration channel.

**Approvals.** In the preview (`e`) or `:XynoSandboxPolicy`, "allow another network host" is an exception of kind `host`, decided like the path exceptions: this launch only, this project (remembered, revocable in `:XynoSandboxApprovals`), or refused, each appended to the decision log (`host` field). Every blocked destination is logged once per host and launch (`decision = "blocked"`) and shown as a warning with the host, so you see what the agent tried.

**Fail closed.** The agent does not start, and `wrap()` returns `nil, reason` ("network egress cannot be enforced (...)"), when `bwrap` cannot create a network namespace (the readiness probe runs with `--unshare-net` and says so), when the socket directory, the relay file or the proxy listener cannot be created, or when `nvim` for the relay is not executable. If the relay does not come up inside the sandbox within 10 s the launcher exits with 125 before the agent runs. `network = "open"` is the explicit opt-out: no namespace, no proxy, the preview and `:XynoSandboxStatus` say OPEN. Any other value (a typo, `true`) is read as filtered.

What does not work in filtered mode: tools that ignore `HTTPS_PROXY` (and anything needing plain HTTP, UDP, `ssh`/`git://`, local services on the host), a corporate upstream proxy (the proxy connects directly), and the agent's first login (log in outside the sandbox, or add `claude.ai` for it). Telemetry hosts are not allowed by default and fail quietly.

## Policy preview

Before a launch the plugin shows the policy it is about to apply, built from the same plan that becomes the `bwrap` command line (`:XynoSandboxPolicy` shows it any time):

- writable paths (project, scratch, the agent and cargo caches)
- read-only paths and the locked git directories
- absent files and directories that are guarded so the agent cannot create them
- hidden credential paths (replaced with empty ones)
- the NAMES of the stripped environment variables (never values; the command's arguments, which hold the prompt, are not shown either)
- the network: `FILTERED` with the host allowlist (and where each entry comes from), or `OPEN`
- the permission-bypass line above

`preview = "always"` shows it before every launch, `"once"` before the first launch of each project, `"never"` not at all. It is an interactive float (`<CR>` or `y` launches, `q` or `n` cancels), so it needs a UI: a headless Neovim never waits for it. `run()` then returns `nil` and starts the job after the confirm (`opts.on_start(job)` gets the id).

### Exceptions

Press `e` in the preview to consider one exception: show one hidden credential path, let one environment variable through, make one more existing path writable, or allow one more network host. Each is decided separately: approve for this launch only, approve for this project (remembered), or refuse. Nothing is approved silently:

- every decision (`approved`, `refused`, `revoked`) is appended to `stdpath("state")/xyno-sandbox/exceptions.log`, one JSON object per line with `ts` (UTC), `project`, `kind` (`env`, `unhide`, `writable`, `host`), `path`, `name` or `host`, `decision` and `scope`. Values of variables are never logged.
- a refused exception leaves the plan exactly as it was (a spec compares the plans).
- an exception that cannot be applied (`/`, `$HOME`, `..`, a path that does not exist, the plugin's own state directory) is logged as refused with the reason.
- remembered approvals are listed and revoked with `:XynoSandboxApprovals`; the state files are `0600` and sit outside every writable path of the sandbox, so the agent cannot edit its own approvals.

## Commands

- `:XynoSandboxStatus` shows how an agent would run here: sandboxed, unsandboxed (and why), or refused (and why, with a fix hint). `:XynoSandboxStatus!` re-runs the readiness probe.
- `:XynoSandboxPolicy [dir]` shows the policy preview for the project (`dir`, default the git root of the current buffer). `!` lists every entry instead of the first 25 of each section. `e` considers an exception.
- `:XynoSandboxApprovals` lists the remembered approvals of every project (`x` revokes the one under the cursor); `:XynoSandboxApprovals revoke {id}` revokes by id; `:XynoSandboxApprovals log` opens the decision log.
- `:XynoSandboxReview [clear] [dir]` shows the files a run planted that were moved into the quarantine and refuses the next launch until `clear`.
- `:XynoSandboxRun {cmd} [args...]` runs the command in a terminal split, wrapped. Arguments are split on whitespace (use `\ ` for a space). The project is Neovim's current directory. If no sandbox is available it prints a one-line error and starts nothing, and a job that cannot start (the program is missing, `jobstart` fails) leaves no empty split behind and releases the sandbox. The program is checked before anything is mounted.

## Readiness

`bwrap` on `PATH` is not a sandbox: unprivileged user namespaces are off on some kernels, restricted by AppArmor, or blocked by a container. `status()` runs the real isolation flags with `true` as the command (`bwrap --unshare-user --disable-userns --unshare-net ... true`; without `--unshare-net` when `network = "open"`) asynchronously with a 5 s timeout and caches the verdict (10 minutes for a success, 30 seconds for a failure). Until it finished `status()` answers `{ mode = "bwrap", ready = "pending" }` without blocking; `wrap()` waits for it once. A failed probe is no backend: the agent is refused, and the reason names the cause (`kernel.unprivileged_userns_clone`, `user.max_user_namespaces`, `kernel.apparmor_restrict_unprivileged_userns`, a container's seccomp profile, a masked `/proc`, a timeout) with the command that fixes it.

## Lua API

```lua
local sandbox = require("xyno_sandbox")

sandbox.status()  -- { mode = "bwrap", ready = "ok"|"pending" }
                  -- | { mode = "unsandboxed", via = "sandbox=false"|"allow_unsandboxed", reason, hint? }
                  -- | { mode = "refused", reason, hint? }        (never blocks)
sandbox.check(cb, force?)  -- run the readiness probe, then cb(status())
sandbox.plan(cmd, project, tmp_dir, { exceptions = {...} })
                  -- the structured plan (writable, readonly, git_locked, masks, guard_files, hidden,
                  -- env_strip, env_kept, network ("filtered"|"open"), net = { hosts, sock, ... }, agent,
                  -- exceptions, notes), or nil, reason when refused
sandbox.default_hosts  -- the default allowlist (copy it to extend)
sandbox.net_mode()     -- "filtered" | "open", as the plan will use it
sandbox.argv(plan)  -- the bwrap command line of a plan (pure)
sandbox.wrap(cmd, project, tmp_dir, { plan = plan })
                  -- string[]? wrapped command, or nil, reason when refused; third value: a handle.
                  -- When explicitly unsandboxed the same `cmd` table comes back.
                  -- `project` and `tmp_dir` are the only writable places of the agent.
                  -- Run the result from Neovim's cwd (it becomes the agent's cwd if inside the project).
                  -- Call handle.release() when the process ended: it deletes the private copy of the
                  -- agent config and the empty placeholders the guards left in the project.
sandbox.confirm(cmd, project, tmp_dir, function(ok, plan_or_reason) end)  -- the launch-time preview
sandbox.run(cmd, { project = ..., tmp_dir = ..., on_start = fn, on_exit = fn })  -- what :XynoSandboxRun does
sandbox.approve(project, kind, value, scope?)  -- log and apply an exception ("once" | "project")
sandbox.refuse(project, kind, value)           -- log a refusal; changes nothing
sandbox.approvals(project?)                    -- remembered approvals
sandbox.revoke(project, id)
sandbox.statusline(), sandbox.statusline_hl()  -- lualine component and its highlight group
sandbox.cleanup()                              -- release every live sandbox (runs at VimLeavePre)
sandbox.scrub_names(env?, file_login?)         -- names of the environment variables that are stripped
sandbox.readonly_paths(project)                -- paths re-bound read-only, and absent dirs masked
```

`xyno_sandbox.plan` is the pure builder behind `plan()`: `build({ project, tmp_dir, cwd, env, home, uid, config, probes, aux, exceptions, cmd })` takes the filesystem as a `probes` table (a table-backed fake in the specs) and returns the plan; `argv(plan)` renders it. Nothing in it touches the disk, so the preview and the launcher cannot drift apart: they print and run the same plan.

### Wrapping an agent command

```lua
local cmd = { "my-agent", "--some-flag", "..." } -- any agent command
local wrapped, err, handle = require("xyno_sandbox").wrap(cmd, project_root, scratch_dir)
if not wrapped then
  error("sandbox: " .. tostring(err), 0) -- fail closed
end
vim.system(wrapped, { cwd = project_root }, function() vim.schedule(handle.release) end)
```

| xynovim | xyno-sandbox |
| --- | --- |
| `vim.g.xynovim_99_sandbox = false` | `setup({ sandbox = false })` |
| `vim.g.xynovim_99_allow_unsandboxed = true` | `setup({ allow_unsandboxed = true })` |
| `require("config.agent_sandbox")` | `require("xyno_sandbox")` |

xynovim passes functions that read those variables, so changing them at run time takes effect immediately.

## How it works

`wrap()` prefixes the command with `bwrap`: a read-only bind of `/`, a private `/dev`, `/proc` and `/tmp`, new user, pid, ipc, uts, cgroup and (by default) network namespaces, nested user namespaces disabled, all capabilities dropped, no controlling terminal (no TIOCSTI injection). The project, the scratch directory, and a short list of agent and cargo cache paths are writable. On top of those binds, git directories (also behind `.git` files and in nested checkouts and submodules down to 8 levels), `.cargo` and `.envrc` of workspace members down to 8 levels, `.cargo`, `.envrc`, `.vscode`, the agent's project directory and the agent's settings, hooks, skills and memory are read-only. In every subdirectory the walk found, the ones that exist of `mise.toml`, `.mise`, `rust-toolchain(.toml)`, `.cargo`, `.envrc`, `.mise.toml`, `.nvim.lua`, `.nvimrc`, `.exrc`, `.claude`, `.mcp.json`, `.vscode`, `.zed`, `.idea`, `.helix`, `.husky`, `.devcontainer`, `.pre-commit-config.yaml`, `.lldbinit`, `.gdbinit`, `.githooks`, `.mvn`, `.pnpmfile.cjs`, `.dir-locals.el` and `.lvimrc` are read-only too. What is absent in the project root and would run unsandboxed when planted (`.git`, `.cargo`, `.vscode`, `.zed`, `.idea`, `.helix`, `.husky`, `.devcontainer`, `.claude`, `.envrc`, `.mise.toml`, `.nvim.lua`, `.exrc`, `.nvimrc`, `.mcp.json`, `.pre-commit-config.yaml`, `.lldbinit`, `.gdbinit`, `.githooks`, `.mvn`, `.npmrc`, `.yarnrc`, `.yarnrc.yml`, `.pnpmfile.cjs`, `.dir-locals.el`, `.lvimrc`) is covered by an empty read-only directory or file for the run, and the launcher removes those empty placeholders when the run ends (`handle.release()`). In the allowlist view `$HOME` is an empty tmpfs with the allowed paths bound back; in the denylist view a list of credential directories (`~/.ssh`, `~/.aws`, browser profiles, keyrings, shell histories and more) is replaced by empty directories or files. `/run` and `/var/tmp` are empty tmpfs. Environment variables whose names look like secrets or cloud credentials are removed: bwrap starts with `env -i` and only the allowed variables, plus `--unsetenv` as a second layer. The agent's user-level config file in `$HOME` is replaced by a private copy limited to the current project. `--die-with-parent` ties bwrap, the agent and the relay to Neovim; the relay also exits on SIGTERM, when its parent is gone and when the proxy socket disappears, and release closes the proxy.

## Residual risks

The filesystem outside `$HOME` is a read-only view of the whole machine (`/usr`, `/etc`, `/var`, `/opt`, other users' readable files), `$HOME` is an allowlist (default) or a denylist, and network egress is limited to a hostname allowlist. It is not a security boundary against a determined attacker.

- the agent's credential file under its config directory in `$HOME` must stay readable (it is bound read-only, so a token refresh inside the sandbox is not saved), so an agent can read that token.
- with `home = "denylist"`, everything unlisted under `$HOME` is readable. With the default allowlist, `$HOME` shows only what is allowed (and what you add, plus `$PATH` entries under `$HOME`, which are shown whole; secret NAMES inside them are hidden, a secret in a file with an ordinary name is not), but the rest of the filesystem (`/etc`, `/var`, `/opt`, `/mnt`, `/srv`, world-readable files of other users) is still readable.
- project secrets are found by file name, and by content for KNOWN token formats only (see "Secrets that no name gives away" for what the scan cannot catch): a password or generic key in an ordinary file, a file past the scan limits, or anything deeper than `scan_depth`, or in `target`/`node_modules`, is readable. A hard link to a hidden file under a name the sandbox shows and the scan did not find stays readable (the plan warns), and so does a hard link to a secret that is not on the credential list. The environment scrub finds secrets by name and by known value formats only. The `~/.claude.json` copy removes what is listed above, not unknown fields (since round 6 it also drops `oauthAccount` ids (`accountUuid`, `organizationUuid`), the top-level `env` map, `awsAuthRefresh`, `awsCredentialExport`, `apiKeyHelper`, `hooks` and the cached feature flags; I did not verify against a real agent which of those fields it would miss, only that the copy parses and keeps the rest; a file that is not a JSON object is not shared at all). A symlink out of the project is listed, not blocked (unless `policy.symlinks = "refuse"`).
- with `network = "open"`, loopback services and abstract sockets are reachable. In filtered mode the host's loopback and abstract sockets are not (own network namespace), and pathname unix sockets are masked (`/run`, `/var/tmp`, `/tmp`, the sockets named by the environment, sockets in the project), but a socket in a directory the sandbox must keep (`policy.keep_run`, a path you added with `policy.writable`/`home_allow`, `/mnt`, `/srv`, `/opt`) is still connectable. With `network = "open"` abstract sockets (X11, some dbus) are reachable too.
- cargo's `registry/src` and `git` are writable, so your own cargo may later build planted code.
- a nested `.git` deeper than 8 levels is not locked (`policy.scan_depth` raises it to 32), and a `.git` the agent creates itself in a new directory is not locked either (the `known limits` spec is an expected failure for that). `target`, `node_modules`, `.venv` and `.cache` are not scanned for secrets (they are searched for sockets). After a kill -9 of Neovim, its private copies (`~/.claude.json` copy, socket directory, git config copies, the empty file that hidden files are bound to) stay in Neovim's temporary directory (`/tmp/nvim.<user>/<id>`, 0600/0700) until the next launch (any `wrap()`) removes the ones that were recorded, and then the emptied directory itself; the placeholders in the project likewise. Every launch has its own empty file and its own copies, removed by `release()`. The in-sandbox relay cannot remove them (the socket directory is mounted read-only inside, and the proxy it talks to died with Neovim), so a Neovim that is never started again leaves them.
- the directory walk stops after 20000 directories; the preview then says so.
- files the project lacks and that are not in the guard list (`bacon.toml`, `rust-toolchain` and `rust-toolchain.toml`: they are locked when present and swept at the end of the run, not guarded while absent, because an empty toolchain file breaks rustup) can be created inside the project during the run. Add them with `policy.guard_files`.
- **subdirectories** (round 6). What EXISTS in a subdirectory is read-only. What is ABSENT is handled in three layers, the strongest first: (1) in the shallowest subdirectories (at most `plan.SUBDIR_MASK_MAX` = 360 mounts, shallowest first, not below a hidden directory or a read-only path) an empty read-only directory is mounted over each absent `.cargo`, `.claude`, `.vscode`, `.git` and an empty read-only file over each absent `.envrc`, `.mcp.json`, `.nvim.lua`, `.mise.toml`, `.exrc`, `.npmrc`, `.yarnrc.yml`, `.dir-locals.el`, `.lvimrc`: `sub/.cargo/config.toml`, `sub/.claude/settings.json`, `sub/.vscode/tasks.json`, a nested `.git/hooks/*` cannot be created there (the empty placeholders are removed when the run ends; while it runs they show up as untracked files in `git status`). (2) Anywhere else in the tree (below the mask budget, deeper than that, other names such as `.zed`, `.idea`, `mise.toml`, `rust-toolchain.toml`) the agent CAN create them during the run. A snapshot of every protected name in the whole tree (`xyno_sandbox.guard`, up to 20000 directories, 40 levels, 1.5 s; `target`, `node_modules`, `__pycache__` and the virtualenvs `.venv` / `venv` are walked in a second pass with a budget of their own, 4000 directories and 0.7 s; `.git` content is not entered, only a new nested `.git` counts) is taken at launch and compared when the run ends: each NEW protected name is copied into `stdpath("state")/xyno-sandbox/quarantine/`, removed from the project, and the project is marked for review. (3) The next launch for that project is REFUSED until you looked (`:XynoSandboxReview`) and ran `:XynoSandboxReview clear`. What remains: during the run itself a planted file exists (a tool of yours that runs meanwhile would use it); a name you create yourself while the agent runs is quarantined too (the copy is kept); nothing is swept after a kill -9 of Neovim (no end of run), nor when another sandbox of the same project is still running (the last one to end compares, but its snapshot also contains what the first one planted); **the walk bounds (round 7).** A bound that stops the walk is no longer silent. If the walk at the END of a run stops at a bound (20000 directories, 1.5 s, 40 levels, or the 4000 directories / 0.7 s of the second pass) although it did not at launch, the tree grew past what can be checked, so the project is marked for review like a planted file (the notice and `:XynoSandboxReview` name the bound; `clear` allows the next launch) and the next launch is refused. If the walk was already stopped at launch (a tree that big anyway: a large `node_modules` often is), nothing can be compared beyond the bound and the end-of-run notice says so at INFO level: a name planted beyond it is NOT found. A slow disk can make the time bound trip on its own; the cost is one `:XynoSandboxReview clear`. **A directory renamed during the run** (`mv sub sub_old`, which Linux allows for the parent of a bind mount) is recognised by the inodes of the protected names (same device and inode under a new path = moved, not created): the user's own `.cargo`, `.envrc`, `.vscode` stay where they went, nothing is quarantined or marked (unless their content changed: round 8 below), and the empty placeholders the masks left in the renamed directory are removed. **Names added in round 7**: `.githooks`, `.mvn`, `.pnpmfile.cjs`, `.dir-locals.el`, `.lvimrc` are read-only when present (root and subdirectories) and `.githooks` / `.mvn` are masked when absent at the root; `.npmrc`, `.yarnrc`, `.yarnrc.yml` (`script-shell`, `yarnPath` run a program) are hidden when present (they usually hold a token) and guarded with an empty read-only file when absent at the root (`.npmrc`, `.yarnrc.yml`, `.dir-locals.el`, `.lvimrc` also in the shallow subdirectories) and swept everywhere; `conftest.py`, `bunfig.toml`, `lefthook.yml` are listed with the editable files and their changes reported. **Round 8: content is compared, not only names.** (1) Every protected name (and everything below a protected directory, up to 400 entries and 6 levels, files up to 128 KB; larger files by size and mtime) is hashed at launch. A protected name that MOVED during the run (same inode under a new path, for example `mv sub sub_old`) used to be trusted whatever was inside; now its content is compared with what it was: unchanged = only "moved"; a new file inside it or a changed file = **tampered**, reported at ERROR level with the lines added and removed, and the project is marked for review like a planted name (the moved directory is NOT deleted: it holds the user's own files; the copy for review is the diff in the notice, and `git diff` / your backup are the original). (2) An EXISTING protected name that changed, however deep in the tree (below the mask depth, beyond the 400 locked directories, where it is not read-only), is found by content, so a file rewritten with the same size and its mtime put back is reported too; the notice lists the file with lines added and removed. It is a notice, not a mark: your own edit of an `.envrc` while the agent runs looks the same, and refusing the next launch for that would punish the normal case. (3) If a planted name cannot be removed because the agent made its parent (or something inside it) `chmod 555` / `000`, the quarantine gives the owner access, copies, removes, and puts the parent's mode back; a name that still cannot be removed (for example a parent that is not yours) is named in the notice and in the review mark. An empty placeholder that cannot be removed is handled the same way. A planted file that is NOT empty is always quarantined, however read-only it is; only an EMPTY read-only file or an EMPTY directory is treated as the sandbox's own leftover. **Names added in round 8**, researched (links and dates below): read-only when present, at the root and in every subdirectory, and swept when absent: `.devcontainer.json` (`initializeCommand` runs on the host), `.bazelrc` / `.bazelversion` / `.bazeliskrc`, `.lefthook/`, `.cargo-husky/`, `.sbtopts`, `.jvmopts`, `.bundle/`, and `.gitmodules` in subdirectories (it was already locked at the root). Editable, reported with lines added and removed when changed (like `Makefile`): `gradle.properties` (`org.gradle.jvmargs`, `org.gradle.java.home`), `gradle-wrapper.properties`, `build.gradle(.kts)`, `settings.gradle(.kts)`, `gradlew`, `mvnw`, `pom.xml`, `build.sbt`, `Gemfile`, `Rakefile`, `.rspec`, `Procfile`, `Procfile.dev`, `.tmuxp.yaml`, `.tmuxinator.yml`, `lefthook-local.yml`, the version selectors `.nvmrc`, `.node-version`, `.python-version`, `.ruby-version`, and `.gitattributes`. **Researched and NOT locked, each with the reason:** `.gradle/init.d` does not exist as an auto-loaded location: Gradle loads init scripts from `$GRADLE_USER_HOME/init.d` and `$GRADLE_HOME/init.d` ([docs.gradle.org init scripts](https://docs.gradle.org/current/userguide/init_scripts.html), read 2026-11-12), both outside the project; `.gitattributes` alone cannot run anything, the `filter` attribute only names a driver that must be defined in git configuration (`.git/config` is locked; [git-scm gitattributes](https://git-scm.com/docs/gitattributes), 2026-11-12); `.gitconfig` in a project is not read by git; `.editorconfig`, `rustfmt.toml`, `clippy.toml`, `.prettierrc` run nothing; `.envrc` is covered, `.direnv/` is only cache (an `.envrc` that put it on `PATH` is the `.envrc`); `.netrc` holds credentials, not commands, and the content scan hides files that contain a token; `.terraform/` holds provider binaries that `terraform` runs, but `terraform init` writes it, like `target/`: it cannot be locked and a binary placed there is only found if it is a protected name (it is NOT); `*.code-workspace` and `*.sublime-project` (a glob, not a name: not looked for); `Dockerfile` and `docker-compose.yml` run only when you start them (not looked at); `.tmuxp.yaml`, `.tmuxinator.yml` and `Procfile` likewise, but they are reported when changed; `build.rs`, `Cargo.toml`, `package.json` scripts, `Makefile`, `justfile`, `conftest.py`, test and bundler configs (`jest.config.js`, `vite.config.ts`, `webpack.config.js`) are code the agent has to write, only reported where listed; and `.bazelrc` is read-only, so an agent that must change bazel flags cannot (use `policy.writable` after reading the preview). The sources for the new names: [devcontainer.json reference: "initializeCommand ... run on the host machine"](https://containers.dev/implementors/json_reference/), [bazelrc: the workspace `.bazelrc` is read](https://bazel.build/run/bazelrc), [Gradle build environment: `gradle.properties` in the project root, `org.gradle.jvmargs`](https://docs.gradle.org/current/userguide/build_environment.html), all read on 2026-11-12. A claim about `.lefthook/`, `.cargo-husky/`, `.sbtopts`, `.jvmopts` and `.bundle/` rests on those tools' conventions as I know them; I did not fetch a page for each. **Not covered, stated plainly:** `package.json` scripts, `Makefile`, `justfile`, a `conftest.py`, `build.rs` and `Cargo.toml` are agent-editable by design and only reported after the run; a name outside every list in this README is not looked for.
- **editable files that run later** (`plan.REVIEW_NAMES`: `Makefile`, `justfile`, `package.json`, `Cargo.toml`, `build.rs`, `pyproject.toml`, `setup.py`, CI files, every file in `.github/workflows`): the agent has to edit them, so they are not locked; the preview lists the ones that exist (`Agent-editable, runs later on your machine`) and when the run ends the launcher reports which were created, changed or deleted with the number of lines added and removed (hashes at launch against hashes at the end; files over 128 KB are compared by hash only, without a line count). A change is only reported, never undone. Since round 9 the report shows the first six changed lines (`- old` / `+ new`, each cut at 72 characters) of a changed small file, so an edited `.nvmrc`, `.gitattributes` or `init.gradle` is visible without opening it; `init.gradle(.kts)` was added to the list. **Build sources** (`plan.REVIEW_TREES`: `buildSrc/` and `build-logic/` at any depth, which Gradle compiles and runs before every build) are recorded as a whole (content hashes of up to 400 entries, six levels) and a created, changed or deleted tree is reported at ERROR level with the files that differ and the lines added and removed. **`node_modules/.bin`** of the project and its workspaces (not of dependencies; up to 500 entries each, recorded inside the `node_modules` walk and therefore under that walk's budget) is compared by link target or content hash: what was added, changed or removed is listed; a regular file or a link that leaves `node_modules` (absolute, or `../../`) is ERROR level, a link into `node_modules` (what `npm install` makes) a warning. Both are REPORTS, not prevention: the agent can still write them during the run (an install has to), and nothing is undone. Not covered: the content of `.gradle/init.d` (a build cache directory, written on every build), sources of an included build under another name, and dependencies' own `.bin`.
- the placeholders of the guards are removed when the run ends; after a crash of Neovim they stay until the next launch (of any project) removes the ones that are still empty. The masks inside the agent's config directory are shared by all projects and stay.
- an approved exception (or `policy.writable`) is checked against the plan at hand; a later change of the policy (a new lock over the same path) turns it into an ignored entry, shown as IGNORED in the preview.
- the data of `/proc/<pid>` of processes outside the sandbox is invisible (own pid namespace), but the kernel's world-readable files in `/proc` and `/sys` (cpu info, mounts of the sandbox) are not hidden.
- **egress limits (filtered mode)**:
  - the agent can still read its own token (it must) and anything readable under `$HOME`, and send it to an allowed host: `api.anthropic.com` is allowed because the agent needs it, and a request body or an API key of an attacker's account is indistinguishable from legitimate traffic. The allowlist narrows where data can go, it does not make the readable data safe.
  - allowed hosts that accept arbitrary uploads (a registry with publishing, `github.com` if you add it, a wildcard on a shared domain) are exfiltration channels. Keep the list short.
  - the check is on the CONNECT host name; there is no TLS interception, so the TLS SNI and HTTP `Host` inside the tunnel are not compared with it. Domain fronting through a CDN that serves several names on one address is not detected.
  - the proxy's own lookup of an allowed name is DNS traffic from your machine (the resolver sees allowed names only); with a wildcard entry the labels below the suffix reach your resolver.
  - the proxy is not rate limited beyond 256 concurrent connections; a connection idle for 30 minutes is closed.
  - a program that is allowed to talk to the relay can open a CONNECT to any allowed host; it cannot change the list (it lives in Neovim, not in the sandbox).
  - the proxy and the relay need a working `nvim` binary at the same path inside the sandbox (an AppImage that needs FUSE does not work: the agent is refused).
- `network = "open"` restores the old behaviour exactly: nothing restricts the network, the preview says OPEN.
- an approved exception (`unhide`, `writable`, `env`) widens the policy for that launch or, when remembered, for that project until revoked; the log tells what and when, it does not make the exception safe.

## Platform status

- Linux: the specs in this repository run on Linux (`nvim -l tests/run.lua`); that is the only platform where the sandbox works and the only one I claim.
- Windows and macOS: there is no bubblewrap, so `wrap()` refuses and nothing starts. In the original xynovim CI the sandbox spec is skipped on both by design, and the refusal was exercised by a separate spec there. `tests/failclosed_spec.lua` ports that refusal check without an OS gate, but this repository's CI only runs on Linux, so on Windows and macOS it is not run here.
- Windows guards from the source stay in place (the module loads without a user id).
- Sandbox specs that need a working user namespace skip with a message on machines that restrict them.
- Known limits that are tested as the correct behaviour are `xfail` specs: reported as `XFAIL` with their reason, counted separately, and a failure (`XPASS`) as soon as one starts passing.

## Tests

See [tests/README.md](tests/README.md) for the harness (`skip`, `pending`, `xfail`).

The runner is hermetic: it ignores the caller's `TMPDIR` (scratch is `/tmp/xyno-run-*`; a deep `TMPDIR` used to push the proxy's socket path over the 107 bytes of `AF_UNIX`), prefers a short base for the fake home, and creates a private root outside `/tmp` with a fake `$HOME` (fake agent credentials, nothing of yours), runs every spec file in a child that uses it, deletes it afterwards, and FAILS the run (killing the process) when a `bwrap` or relay process created by a spec file is still alive when that file finished. Without a working bubblewrap (a CI container without user namespaces) the specs that run commands inside a sandbox skip with the reason and the plan/argv specs still run; when the runner's own probe finds bubblewrap working, a sandbox that then does not start is a FAILURE, not 90 skips. A spec file that hangs is killed after 240 s (`XYNO_TEST_FILE_TIMEOUT_MS`) and fails the run. Specs that bind a unix socket below `$HOME` skip when that path would exceed the socket path limit (a very deep real `$HOME`); the suite also passes from a checkout under `/tmp`.

```sh
nvim -l tests/run.lua                       # every tests/*_spec.lua, one headless nvim each
LAZY_PATH=/path/to/lazy.nvim nvim --headless -u tests/e2e/smoke.lua   # lazy.nvim smoke test
```
